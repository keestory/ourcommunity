# 격리된 체험 배포 준비

사용자는 기존 초안 [PR #1](https://github.com/keestory/ourcommunity/pull/1)을 이어서 iPhone 브라우저에서 열 수 있는 체험 배포를 승인했다. main 병합, 새 계정·결제·명시적 약관 수락, 외부 비밀키 발급·지속 접근 설정 변경은 이 승인에 포함하지 않는다.

2026-10-30 UTC 현재 상태는 **로컬 컨테이너 검증 Pass / 공개 배포 Blocked**다. 이 문서의 설정 예시는 발급된 공개 URL이 아니다. 배포 승인 자체는 받았으며, 추가 승인 대기가 아니라 현재 연결된 호스팅과 저장 구조의 불일치가 차단 원인이다.

## 환경 확인 결과

- 이 작업에 노출된 도구에는 호스팅 배포나 공개 포트 전달 기능이 없다.
- 부모 작업이 기존 Vercel Hobby 팀(`keestory91-6294s-projects`) 접근을 확인했다. 아직 ourcommunity 프로젝트 연결은 없으며 이 작업 안에는 해당 connector/CLI가 없다. Vercel 함수의 수명과 저장 방식은 아래 호환성 판정에서 구분한다.
- Docker 28.4.0은 로컬에서 동작한다. 이는 인터넷에서 접근 가능한 호스팅·도메인이 있다는 뜻은 아니다.
- Python과 Node 공식 기반 이미지는 가져올 수 있다. 외부 임시 터널 공식 문서 접근은 프록시 403으로 실패했으며 다른 경로로 차단을 우회하지 않는다.
- 기존 초안 PR은 다시 만들지 않는다. 브랜치와 PR head는 Git 원격 ref로 확인할 수 있지만, 이 실행 환경의 GitHub API 연결은 여전히 별도 제약이 있다.

현재 구현에 필요한 배포 대상은 **기존 권한으로 사용할 수 있고 추가 비용이 없는 단일 인스턴스 Python 또는 Docker 장기 실행 프로젝트/서버**다. HTTPS 주소, 프로젝트 식별자와 승인된 배포 접근 경로가 필요하다. 인프라 런타임의 자격증명 표시는 사용자 앱을 배포할 권한으로 해석하지 않는다.

## 체험 모드의 경계

`PREVIEW_MODE=1`은 기존 로컬 개발 모드와 분리한다. API와 빌드한 React 화면을 한 Python 프로세스·한 origin에서 제공한다. 프런트엔드만 배포하고 전체 제품이라고 표시하지 않는다.

- 방문자마다 독립된 합성 데이터 SQLite를 만들며, 서버가 발급한 HttpOnly guest cookie로만 선택한다. 다른 방문자의 샘플 ID가 같아도 DB는 공유하지 않는다.
- 같은 브라우저의 역할 전환과 새로고침은 현재 체험 공간을 유지한다. 역할 선택은 실제 신원 인증이 아니다.
- 일반 회원가입·비밀번호 로그인과 외부 초대·공개 공유는 체험 모드에서 지원하지 않는다. 실제 개인정보를 수집하는 가입 화면을 제공하지 않는다.
- 체험은 기본 1시간이고 프로세스 종료·재시작 시 데이터가 사라진다. 생산 데이터 영속성이나 장기 저장을 약속하지 않는다.
- 기본 상한은 동시 방문자 16명, 새 공간 생성 전체 분당 6개, 방문자별 요청 분당 360개·진행 요청 8개, 쓰기 분당 60개·체험 전체 500개다. 본문은 스트림을 포함해 16KiB로 제한하고, 서버 전체 동시 요청은 128개로 제한한다. 제한 도달 시 오류를 표시하며, 다른 방문자의 공간을 재사용하지 않는다.
- `PUBLIC_ORIGIN`은 정확한 origin 하나다. 외부 주소는 HTTPS여야 하고 wildcard·경로·임의 origin을 허용하지 않는다. HTTP는 로컬 시험용 loopback 주소만 허용한다.
- TLS는 대상 호스팅이 종료한다. 공개 Host 헤더가 API까지 유지되어야 한다. 외부 origin일 때 쿠키는 Secure이며 프록시 헤더로 신뢰 경계를 넓히지 않는다.
- 컨테이너는 단일 worker·단일 인스턴스 전용이다. 여러 worker나 자동 수평 확장은 namespace 공유와 요청 라우팅을 별도로 설계하기 전에는 지원하지 않는다.

모든 데이터는 가상이다. 외부 로그인·OS 푸시·실제 시설/예약·고객 운영 서비스로 광고하지 않는다. 이 경계는 소규모 체험의 자원 사용과 방문자 간 노출을 제한하기 위한 것이며 공개 서비스의 모든 남용·가용성을 보장하는 정책은 아니다.

## 컨테이너와 호스팅 요구

Docker 빌드는 Node 단계에서 정적 화면을 만들고 Python 단계에서 API와 화면을 함께 제공한다. 빌드 문맥은 필요한 제품 소스·의존성 선언만 허용하며 `.env`, DB, git 이력, 로컬 의존성·테스트 출력은 제외한다. 런타임은 비루트 사용자로 실행한다.

호스팅에는 TLS, `PUBLIC_ORIGIN`, 실행 포트 `PORT`, 임시 파일을 쓸 수 있는 공간이 필요하다. SQLite는 이 체험에서 임시 저장소로만 사용한다. 파일 쓰기가 금지된 프런트엔드 전용 또는 짧은 함수 호출 환경은 현재 서버를 그대로 실행할 수 없다. 영구 볼륨을 추가하거나 유료 플랜을 고르지 않는다.

## Vercel 호환성 판정

Vercel에서 Python/ASGI 실행이 가능하더라도 **현재 체험 구조는 배포 NO-GO**다. 방문자 cookie와 DB 경로를 연결하는 registry는 `PreviewStore.guests` 프로세스 메모리에 있고 SQLite는 그 프로세스의 임시 디렉터리에 있다. 다른 인스턴스나 콜드스타트에서는 같은 cookie를 알 수 없어 401과 세션 초기화가 발생한다. `/tmp` 파일만 우연히 남아도 registry가 복구되지 않는다. 고정 URL이나 함수 실행 시간 설정은 이 저장·라우팅 문제를 해결하지 않는다.

Vercel을 선택하려면 기존 승인된 공유 저장소와 서버리스용 namespace·세션·정원 트랜잭션·요청 한도 설계로 변경해야 한다. 다른 프로젝트의 데이터나 자격증명을 임의로 재사용하지 않는다. 새 DB 계정·비밀키·지속 접근이 필요하면 별도 승인이 필요하다. 현재 코드에 `vercel.json`만 추가해 안정적인 전체 앱 배포로 표시하지 않는다.

## 로컬 컨테이너 검증 명령

다음은 공개 배포 명령이 아니라 loopback 시험 예시다.

```bash
docker build -t ourcommunity-preview:local .
docker run --rm --name ourcommunity-preview-local \
  --read-only --tmpfs /tmp:rw,nosuid,noexec,size=256m \
  --cap-drop ALL --security-opt no-new-privileges \
  --memory 512m --cpus 1 --pids-limit 128 \
  -p 127.0.0.1:8088:8080 \
  -e PUBLIC_ORIGIN=http://127.0.0.1:8088 \
  ourcommunity-preview:local
```

소규모 체험 예산은 메모리 512MiB·임시 디스크 256MiB를 기준으로 한다. 최대 UTF-8 본문의 반복 저장 비용과 SQLite index/WAL 여유를 고려해 방문자 16명·총 쓰기 500회로 낮췄다. 더 작은 디스크나 더 큰 방문자 한도를 선택하려면 자원 시험을 다시 해야 한다. 영구 볼륨은 연결하지 않는다. 실제 호스팅에서는 원본 포트를 직접 공개하지 않고 TLS 라우터 뒤에서 접근시킨다.

이 클라우드의 기본 Docker buildx 설정 경로는 읽기 전용이어서 로컬 시험에는 `/tmp`의 임시 `DOCKER_CONFIG`를 사용한다. 빌드 중 패키지 네트워크는 기존 환경 프록시 정책을 유지하며 프록시 값·자격증명을 이미지나 저장소에 기록하지 않는다.

해당 프록시의 DNS와 인증서가 컨테이너 기본 환경에 없어서, 검증 빌드에는 기존 프록시 환경변수 전달·동일 프록시 호스트의 DNS 매핑·기존 공개 CA bundle의 BuildKit `build_ca` secret mount를 사용했다. 다른 프록시로 바꾸거나 TLS 검사를 끄지 않았다. `build_ca`는 필요할 때만 전달하는 빌드 입력이며 이미지에 저장하지 않는다. 일반 네트워크에서는 생략할 수 있다.

## 검증과 게시 조건

1. 기존 테스트를 보존하면서 방문자 간 분리·쿠키/Origin·만료·작성 한도·정적 경로·API 경계 시험을 실행한다.
2. Docker 이미지가 실제 빌드되고 비루트로 실행되는지, API와 SPA가 한 origin에서 동작하는지 확인한다.
3. 모바일 브라우저 크기에서 역할 선택→채팅 작성→신청→운영자 출석→공동 성장→새로고침을 확인한다. 별도 브라우저의 공간에는 변화가 없어야 한다.
4. 실제 호스팅 배포 후 그 **공개 URL**에서 같은 흐름과 런타임 로그를 확인한다. 로컬 Chromium 성공은 iPhone 실기기나 공개 URL 검증을 대신하지 않는다.
5. 이 검증을 통과한 URL·배포 revision·제한사항만 반환한다. 대상 호스팅이 없으면 준비한 산출물과 정확한 연결 조건을 남긴다.

## 정확한 남은 단계

1. 기존 단일 인스턴스 Python/Docker 호스트의 프로젝트·HTTPS 주소·승인된 배포 경로가 제공되면 위 컨테이너로 배포하고 공개 주소에서 다시 확인한다.
2. Vercel을 유지한다면 ourcommunity 전용으로 사용 가능한 공유 저장소 유무와 권한부터 확인한다. 기존 승인 범위에서 없으면 새 저장소/자격증명/접근 설정에 대한 승인과 서버리스 저장·세션 변경이 필요하다. 현재 프로젝트 생성만으로 해결되지 않는다.
